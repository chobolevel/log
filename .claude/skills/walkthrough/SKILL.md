설계 대조와 읽기 가이드를 만든다. 인자: $ARGUMENTS

인자는 모두 생략할 수 있고 순서는 상관없다. 토큰은 이렇게 해석한다: `.md`로 끝나면 설계 문서 경로, `S-숫자` 형태면 슬라이스 ID, 그 외에는 base다.

## 입력 정하기

1. **base**: 인자에 없으면 `origin/main`이 있을 때 그것, 없으면 `main`. 비교 기준은 `git merge-base HEAD <base>`로 구한다.
2. **변경 내용**: `git diff <merge-base>`(커밋과 미커밋 변경 포함)를 본다. 새 파일은 `git status --short`로 확인한다.
3. **설계 문서**: 인자로 받은 경로. 없으면 변경 파일 중 `docs/design/*.md`(README.md, _template.md 제외)가 있는지 본다. 그래도 없으면 설계 문서 없음 모드로 진행한다.
4. **슬라이스**: 인자로 받은 ID만 대상으로 한다. 없으면 문서 전체를 대상으로 한다. 대상이 아닌 슬라이스의 항목은 "대상 아님"으로 둔다.
5. **함께 읽을 것**: `CLAUDE.md`, `docs/design/README.md`(위험도 기준), 설계 문서.

## 절차

1. 변경 파일 목록을 만들고 주 코드, 테스트, 설정, 문서로 나눈다.
2. **설계 문서 모드**
   - 대상 슬라이스의 테스트 케이스마다 대응하는 테스트를 diff와 기존 테스트에서 찾아 매핑한다.
   - "영향 범위"와 슬라이스 정의를 diff와 비교해 범위 밖 변경, 설계에 있는데 diff에 없는 항목을 찾는다.
   - "결정 사항"과 구현이 어긋나는 곳을 찾는다.
3. **설계 문서 없음 모드**: 2번을 생략하고 그 사실을 출력 맨 위에 적는다. 변경된 주 코드마다 대응 테스트 변경이 있는지만 확인한다. 출력의 "범위 점검"과 "설계와 다르게 구현된 것"은 각각 "해당 없음(설계 문서 없음)" 한 줄로 쓴다.
4. **읽기 가이드**: 변경된 주 코드를 위험도순으로 정렬한다. 위험도가 높은 곳은 항목별로, 낮은 곳은 묶어서 한 행으로 쓴다. 테스트 파일은 읽기 가이드 대상이 아니라 매핑의 근거로 쓴다.

## 출력 형식

```markdown
# 워크스루: <기능 또는 슬라이스>

기준: 설계 문서 <경로> / 슬라이스 <ID 또는 전체> / base <sha>
(설계 문서 없음 모드면 "설계 문서 없음: 설계 대조 생략" 명시)

## 1. 읽기 가이드 (위험도순)

| 순서 | 위치 (파일:줄) | 위험도 | 왜 읽어야 하나 | 머지 전에 설명할 수 있어야 할 것 |
|---|---|---|---|---|

## 2. 설계 대조

### 테스트 케이스 매핑

| 설계 문서의 케이스 | 대응 테스트 (파일:테스트명) | 상태 |
|---|---|---|

상태는 충족 / 부분 / 없음 / 상충(설계와 반대로 구현됨) / 판단불가 중 하나.

### 범위 점검

- 영향 범위 밖 변경:
- 설계에는 있는데 diff에 없는 것:

### 설계와 다르게 구현된 것

없으면 "없음".

## 3. 요약

한 줄 판정과, 작성자가 먼저 확인할 것 최대 3가지. 확인할 것은 설계 대조 결과(누락, 상충, 범위 이탈)와 위험도 높은 구간에서만 고른다. 결함이 의심되는 것은 여기에 올리지 말고 "참고"에만 쓴다.

참고: 읽다가 본 명백한 결함이 있으면 한 줄씩 (최대 3개, 없으면 생략)
```

"머지 전에 설명할 수 있어야 할 것"은 코드에 근거한 구체적인 질문으로, 행당 최대 2개, 각 한 문장으로 쓴다. 예: "이 검증이 엔티티 생성 경로 중 어디서 호출되는지", "실패하면 어떤 예외가 어디까지 전파되는지".
