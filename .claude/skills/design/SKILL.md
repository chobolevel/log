설계할 기능: $ARGUMENTS

이 skill의 산출물은 `docs/design/<slug>.md` 하나다. 코드는 쓰지 않는다.

## 규칙

- 쓰는 파일은 `docs/design/<slug>.md`(필요하면 `decisions/` ADR)뿐이다. 소스 코드, 테스트, 설정은 수정하지 않는다.
- 개발자끼리 설계를 논의하듯 진행한다. 사용자가 제안한 방향대로만 가지 않는다. 더 나은 방향이 있으면 대안과 트레이드오프를 근거와 함께 제안하고, 논의로 결정한다.
- 합의되기 전에는 문서를 쓰지 않는다. 코드를 읽어서 알 수 있는 것은 묻지 않는다.

## 절차

1. **컨텍스트 파악 (읽기 전용)**: `CLAUDE.md`, `docs/conventions/`, `docs/design/README.md`(위험도 기준), `decisions/`, 관련 코드를 읽는다. 겹치는 기존 설계 문서가 있는지 확인한다. 탐색 범위가 넓으면 Explore subagent에 맡겨 컨텍스트를 아낀다.
2. **인터뷰**: `AskUserQuestion`으로 어려운 부분, 엣지 케이스, 실패 시 동작, 트레이드오프, 비범위를 묻는다. 뻔한 질문은 하지 않는다. 결정이 갈리는 지점은 대안 2~3개와 추천안을 함께 제시한다.
3. **슬라이스 분해**: 초안을 제시하고 합의한다. 슬라이스는 동작 변화 하나이고, 독립적으로 머지·롤백할 수 있고, 완료 조건을 테스트 케이스로 쓸 수 있어야 한다. 라인 수는 기준이 아니다.
4. **테스트 케이스와 위험도**: 슬라이스마다 단위 / API·통합 시나리오 / 경계값·예외를 적는다. 위험도는 `docs/design/README.md` 기준으로 매기고 근거를 한 줄 적는다. 위험도 "높음"에는 PR 리뷰에서 정독할 지점을 지정한다. 끝단 검증은 자동화된 시나리오로 정의하고 수동 확인으로 대체하지 않는다.
5. **작성**: `docs/design/_template.md` 구조 그대로 `docs/design/<slug>.md`를 만든다. slug는 소문자와 하이픈이다. 상태는 "초안"으로 시작하고, 모든 슬라이스에 테스트 케이스와 위험도가 있고 열린 질문이 비었을 때만 사용자 확인을 받아 "확정"으로 바꾼다.
6. **마무리**: 문서 경로, 슬라이스 목록, 남은 열린 질문을 요약한다. 슬라이스별 구현은 새 세션에서 이 문서를 읽고 시작하도록 안내한다. 커밋은 `CLAUDE.md`의 커밋 흐름을 따른다.
