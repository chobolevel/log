# 기록 피드 (최신순 cursor → 점수 → 사전 계산)

- 상태: 초안
- 작성일: 2026-10-29
- 관련: [모듈·패키지·의존 구조 ADR](../../decisions/module-and-package-structure.md), 수평 확장 ADR(작성 전, 3단계 슬라이스와 함께 결정)

---

## 배경과 목표

기록을 한곳에서 이어서 볼 수 있는 피드를 만든다. 대형 트래픽 서비스에 실제로 도입한다는 전제로, 한 번에 완성하지 않고 단계별로 키운다.

1. **최신순 + cursor 페이징**: 공개 기록 전체를 최신순으로, 깊은 페이지에서도 비용이 일정하게
2. **점수 도입**: 전역 점수(좋아요·조회·시간 감쇠) → 사용자별 개인 가중
3. **사전 점수 계산**: 점수를 미리 계산해 두고, 스냅샷으로 페이지 일관성을 확보

끝나면 다음이 가능해진다.
- 비로그인과 로그인 사용자 모두 피드를 받는다. 로그인 사용자는 내가 쓴 기록과 이미 조회한 기록을 제외한 피드를 본다.
- 기록 수가 늘어도 피드 조회 비용이 페이지 깊이와 무관하다.
- 이후 단계가 같은 엔드포인트와 패키지 위에서 점수와 사전 계산을 얹는다.

**진행 방식**: 문서 하나로 간다. 1단계(S-1~S-3)는 슬라이스와 테스트 케이스를 확정하고, 2·3단계(S-4~S-6)는 방향과 윤곽만 적는다. 설계가 바뀌면 코드보다 문서를 먼저 고치고, 2·3단계는 착수 전에 이 문서의 해당 슬라이스를 구체화한다.

## 결정 사항

| 결정 | 선택 | 대안 | 선택 이유 |
|---|---|---|---|
| 정렬과 cursor | `id DESC`. cursor는 마지막으로 **스캔한** 기록 id를 불투명 문자열(Base64)로 인코딩 | `created_at + id` 복합 cursor / offset | PK는 단조 증가하고 유일해서 동률이 없고 PK 인덱스만으로 조회된다. offset은 깊어질수록 읽는 행이 늘고, 도중에 기록이 등록되면 중복·누락이 생긴다. 새 기록은 더 큰 id라 이미 받은 페이지 뒤쪽에 영향이 없다 |
| 응답 형식 | `data`와 `nextCursor`(마지막 페이지면 null). `totalCount` 없음 | `totalCount` 포함 / `hasNext` 불리언 | 전체 개수 `COUNT`는 피드에서 쓸모가 없고 비용만 든다. `nextCursor`가 `hasNext`를 겸한다. 한 건 더 조회(`size+1`)로 다음 페이지 유무를 판단한다 |
| 메서드 이름 | 서비스와 저장소 모두 `searchRecordFeeds(...)` | 서비스 `searchRecordFeeds`, 저장소 `searchFeedRecords` / `fetchRecordFeed` | 이 코드베이스는 서비스와 저장소가 같은 이름을 쓴다(`searchRecords`, `searchSubjects`, `searchEmotions`, `searchNotifications`). 호출 흐름에서 이름이 이어지고 검색하기 쉽다. "피드 항목 하나"를 `RecordFeed`로 보면 `searchRecordFeeds`는 `searchRecords`와 같은 규칙이다. 저장소가 `Record` 엔티티를 반환하는 점은 `searchRecords`도 같다 |
| cursor 인코딩 | 정책을 담은 범용 `UrlSafeBase64`(`api/common/web`, `object`)를 쓴다. 인코딩은 URL 안전 알파벳·패딩 없음·UTF-8, 디코딩은 URL 디코더로 엄격하게 하고 실패하면 `null`을 돌려준다. 기록 id 해석과 `INVALID_FEED_CURSOR` 변환은 `RecordFeedCursorConverter`에 남긴다 | cursor 전용 코덱 / 호출 지점에서 `java.util.Base64`를 직접 사용 | cursor는 응답으로 내려간 뒤 쿼리 파라미터로 되돌아오는 값이다. 정책(알파벳·패딩·문자셋)이 호출 지점마다 흩어지면 일관성이 깨지고, 출력이 URL의 unreserved 문자(`A-Z a-z 0-9 - _`)뿐이면 어떤 위치에서도 퍼센트 인코딩이 필요 없다. 현재 payload(숫자)는 Basic으로도 `+`·`/`가 나오지 않지만 S-4·S-6의 cursor는 숫자만 담지 않을 수 있어 처음부터 못 박는다. `common`의 역할 목록에 `util`은 없으므로 정책의 성격(웹 계약)에 맞는 `common/web`에 둔다. 디코더는 깨진 입력을 예외로 드러내는 URL 디코더를 쓴다(MIME 디코더는 깨진 입력도 빈 값으로 통과시킨다) |
| 응답 항목 타입 | 기존 `RecordResponse` 재사용 | 처음부터 `RecordFeedResponse`로 분리 | S-1~S-4까지 `RecordResponse`와 달라질 필드가 확정된 것이 없다. 피드 전용 필드(예: 노출 이유)가 실제로 필요해지면 `api/record/feed` 안에서 분리한다. 소비자가 피드 컨트롤러 하나뿐이라 분리 비용이 작다 |
| 점수 노출 | 점수는 응답에 노출하지 않는다 | 점수를 응답에 포함 | 점수는 서버 내부의 랭킹 구현이다. 노출하면 공식을 바꿀 때마다 API 계약이 흔들리고, 클라이언트는 순서만 필요하다 |
| 페이지 크기 | 기본 20, 최대 50 | 상한 없음 | 한 요청이 읽는 행과 Redis 배치 조회를 제한한다 |
| 엔드포인트 | `GET /api/v1/records/feed` | `GET /api/v1/feeds/records` | 기록 도메인의 피드이고 새 최상위 기능 패키지(ArchUnit 허용 목록 수정)가 필요 없다. `/records/{id}`와 경로가 겹치지만 리터럴이 우선하며 테스트로 고정한다 |
| 패키지 | `api/record/feed/{controller,service,dto,validator,converter}`. `domain`에는 새 패키지 없음 | 기존 `api/record/` 레이어에 추가 | 피드는 엔티티·리포지토리가 없는 읽기 모델이라 `domain` 서브 도메인이 아니다. 2·3단계에서 점수·스냅샷·스케줄러 클래스가 늘어나므로 `RecordService`와 분리한다. 조회 메서드는 `RecordRepository`에 추가한다 |
| 비로그인 | 허용 (전역 피드). 보안 설정은 `/api/**` 전체가 `permitAll`이라 변경 없음 | 로그인 전용 | 기존 기록 목록도 비인증 공개이고, 이후 개인화가 없는 사용자의 기본 경로가 된다 |
| 노출 정책 | 항상 제외: 비공개, 삭제, **탈퇴(`resigned`) 작성자**의 기록. 로그인 시 추가 제외: 내가 쓴 기록. **공개 `DIARY`는 포함** | `DIARY` 제외 / 탈퇴 작성자 노출 | 기존 목록은 탈퇴 작성자 기록도 노출하지만 피드는 제외한다(단건·목록 동작은 바꾸지 않는다). `DIARY` 제외는 선택되지 않았다 |
| 조회한 기록 제외 | Redis seen-set을 **캐시**로 쓰고, 원천은 DB(`record_views`). seen-set이 비어 있으면 DB에서 최근 조회를 읽어 채운다 (S-3) | 피드 쿼리에서 DB `NOT EXISTS` / 2단계로 미룸 | `record_views`는 조회 요청 트랜잭션에서 동기로 저장되므로 DB는 항상 정확하다. 다만 append-only로 계속 커지는 테이블에 피드 요청마다 `NOT EXISTS`를 거는 것은 대형 트래픽 전제에 맞지 않는다. 좋아요·조회수와 같은 "캐시 + 원천에서 복구" 구조를 따른다 |
| seen-set 포트 | 기록 전용 `RecordSeenProvider`를 `domain/record/provider`에 정의, 구현은 `infrastructure/redis` | `CacheProvider`에 집합 연산 추가 | `CacheProvider`는 문자열 연산 포트로 단순하다. ZSET 연산과 상한·TTL 정책을 거기에 섞지 않는다. ADR 002의 "구현 기술은 `domain`의 포트를 통해서만 쓴다"를 따른다 |
| 인덱스 | S-2에서 **측정 후 필요할 때만** 추가 | 처음부터 복합 인덱스 | 현재 `records`에는 PK와 FK 인덱스뿐이다. 피드 쿼리가 PK 역방향 스캔으로 충분한지는 비공개·삭제가 섞인 대량 데이터로 확인해 봐야 안다 |
| 성능 검증 | 읽은 행 수(`Handler_read_*`)와 실행 계획(`EXPLAIN`)으로 단언하고, 시간은 로그로만 남긴다 | 처리 시간 임계값 단언 / k6 부하 테스트 | 시간 단언은 환경에 따라 흔들린다. 부하 테스트는 이 슬라이스 범위에 넣지 않는다 |
| 점수 순서 | 전역 점수(S-4) → 개인 가중(S-5) | 처음부터 사용자별 점수 | 전역 점수는 사용자와 무관해서 3단계 사전 계산이 단순하다. 개인 가중은 그 위에 요청 시점에 더한다 |
| 페이지 일관성 | 2단계는 best-effort(점수 변동으로 인한 소량 중복·누락 허용), 3단계 스냅샷으로 해결 | 2단계부터 일관성 보장 | 요청마다 점수를 고정하려면 사실상 스냅샷이 필요해 3단계 작업이 당겨진다. 3단계가 필요한 이유가 분명해진다 |

## 영향 범위

**새로 만든다 (S-1)**
- `api/record/feed/controller/RecordFeedController`: `GET /api/v1/records/feed`
- `api/record/feed/service/RecordFeedService`: `searchRecordFeeds(...)`
- `api/record/feed/dto`: 요청(`cursor`, `size`)과 응답(`data`, `nextCursor`). `data`의 항목은 기존 `RecordResponse`를 재사용한다
- `api/record/feed/validator/RecordFeedParameterValidator`: `size` 범위와 cursor 형식. `@QueryObject`는 Bean Validation을 타지 않으므로 검증기에서 한다
- `api/record/feed/converter`: cursor 문자열 ↔ 기록 id
- `api/common/web/UrlSafeBase64`: URL 안전 Base64 인코딩 정책(알파벳·패딩·문자셋)을 담은 범용 유틸
- `domain/record/vo/RecordFeedQueryFilter`: `beforeRecordId`, `excludeWriterId`
- `RecordRepository.searchRecordFeeds(...)`(반환: `Record` 엔티티 목록)와 `infrastructure`의 Adapter·`RecordQuerydslRepository` 구현
- `RecordErrorCode`에 `INVALID_FEED_CURSOR`(`INVALID`) 추가

**새로 만든다 (S-3)**
- `domain/record/provider/RecordSeenProvider`(포트), `domain/record/vo/RecordFeedRedisKey`
- `infrastructure/redis`의 구현. Redis 키는 사용자·비회원별 ZSET(점수=조회 시각), 상한과 TTL은 아래 S-3에서 정한다
- `RecordViewRepository`에 최근 조회 기록 id 조회 추가 (웜업용)

**바뀐다**
- S-3: `RecordViewService.recordView`가 커밋 후 seen-set에 기록한다. 기존 조회수·dedup 흐름은 그대로 둔다
- S-2: 필요하면 `records`에 인덱스 하나를 추가하는 Flyway 마이그레이션(현재 마지막 버전은 V18)

**건드리지 않는 외부 계약**: 기존 기록 API(목록·단건·등록·수정·삭제·조회수), DB 스키마의 컬럼, 이벤트 페이로드, Redis 기존 키.

**알고 있는 사실 (코드로 확인)**
- `record_views`는 조회 요청의 같은 트랜잭션에서 저장된다. Kafka·Outbox는 Redis 조회수 카운터를 재동기화하는 부가 경로다.
- `V8__add_record_views_table.sql`의 테이블 주석은 "Kafka를 거쳐 쌓인다"고 적혀 있어 구현과 다르다. 이 설계는 코드를 기준으로 한다. 주석 정정은 비범위에 적었다.
- `idx_record_views_user_id`는 InnoDB 보조 인덱스라 PK(`id`)를 포함한다. 사용자별 최근 조회를 `id` 역순으로 읽는 웜업 쿼리가 인덱스를 탈 수 있다.

## 슬라이스별 테스트 케이스

구현 전에 이 목록을 확정하고, 테스트를 먼저 작성해 실패를 확인한 뒤 구현한다.

### S-1 공개 기록 최신순 cursor 피드 API

- 단위 (서비스, Kotest `BehaviorSpec` + MockK):
  - cursor가 없으면 첫 페이지: 저장소에서 `size+1`건을 읽고, 초과분이 있으면 응답은 `size`건과 `nextCursor`(마지막 응답 기록 id)
  - 결과가 `size` 이하면 `nextCursor`가 null, 결과가 0건이면 `data`가 비고 `nextCursor`가 null
  - 로그인 사용자의 id가 `excludeWriterId`로, 비로그인은 null로 전달됨
  - 좋아요·조회수는 응답 기록 id 목록으로 배치 조회 1회씩
- 단위 (cursor 변환): 인코딩↔디코딩 왕복, 숫자가 아닌 값·0·음수·깨진 Base64는 `INVALID_FEED_CURSOR`
- 단위 (`UrlSafeBase64`): 한글·구분 기호가 섞인 값까지 왕복, 표준 `Base64`라면 `+`·`/`·`=`가 나오는 값에서 출력이 `A-Z a-z 0-9 - _`뿐이고 패딩이 없음, 패딩이 붙은 입력도 해석, 알파벳 밖 문자·표준 알파벳 문자·UTF-8이 아닌 바이트는 `null`
- 단위 (검증기): `size`가 1 미만이거나 50 초과면 400
- 저장소 계약 (MySQL 컨테이너): `id DESC` 정렬, `id < cursor` 조건, 비공개 제외, 삭제 제외, 탈퇴 작성자 제외, `excludeWriterId` 제외, 공개 `DIARY` 포함, `limit` 적용
- API / 통합:
  - 비로그인 요청이 200
  - 로그인 요청에서 내 기록이 빠짐
  - 기록 45건(공개), `size=20`으로 `nextCursor`를 따라가면 20·20·5건이고 합집합이 전체와 같으며 중복이 없음
  - 순회 도중 새 기록이 등록되어도 이미 받은 페이지와 다음 페이지에 중복·누락이 없음
  - `/records/feed`가 `/records/{id}`로 라우팅되지 않고 `/records/{숫자}`는 기존대로 단건 조회
- 경계값 / 예외: `size=1`, `size=50`, `size=51`(400), 존재하는 최대 id보다 큰 cursor(첫 페이지와 같은 결과), 가장 작은 id를 가리키는 cursor(빈 결과), 기록이 0건

### S-2 대량 시드 성능 검증과 인덱스

- 시드: MySQL 컨테이너에 기록 약 200,000건(공개 약 70%, 비공개 약 15%, 삭제 약 15%, 여러 작성자)을 일괄 삽입
- 실행 계획: 피드 쿼리가 풀 스캔(`type=ALL`)이 아니고 `Using filesort`가 없음
- 읽은 행 수: 첫 페이지와 깊은 페이지(cursor를 시드의 중간·끝 근처로)에서 `Handler_read_*` 합계가 `size`에 대한 상한 이내이고, 두 값의 비율이 작음 (상수는 측정 후 확정해 이 문서에 기록한다)
- 쿼리 수: 한 페이지 응답을 만드는 총 쿼리 수가 `size`에 비례하지 않음 (Hibernate 통계. 현재 변환 과정이 N+1인지는 확인하지 못했으므로 측정 후 상한과 필요 시 수정을 이 슬라이스에서 정한다)
- 대조(로그만, 단언 아님): 같은 깊이의 offset 쿼리의 읽은 행 수와 시간을 남긴다
- 인덱스를 추가하는 경우: 인덱스 없이 위 단언이 실패하는 것을 먼저 확인(레드)하고, 마이그레이션 후 통과. `ddl-auto: validate` 스키마 검증도 통과
- 경계값 / 예외: 마이그레이션이 기존 데이터가 있는 테이블에 적용되어도 실패하지 않음 (V1~V18 적용 후 V19)

### S-3 조회한 기록 제외

- 단위 (서비스):
  - seen에 있는 기록은 응답에서 빠지고, 빠진 만큼 추가로 스캔해 `size`를 채움
  - 스캔 라운드 상한에 도달하면 부분 페이지와 `nextCursor`(스캔한 마지막 id)를 반환
  - 스캔한 후보가 모두 seen이어도 끝이 아니면 `data`가 비고 `nextCursor`가 있음
  - 스캔 결과가 배치보다 적으면 끝이므로 `nextCursor`가 null
  - seen 조회(Redis)가 실패하면 필터 없이 응답함 (피드는 가용성 우선)
  - 비회원은 `guestId`로, 식별자가 없는 요청은 제외 필터를 적용하지 않음
  - seen-set이 비어 있으면 DB 최근 조회로 웜업하고, 조회 이력이 없는 사용자는 표식을 남겨 매 요청 재웜업하지 않음
- 단위 (`RecordViewService`): 조회 성공의 커밋 후에 seen-set 기록이 호출됨, seen 기록이 실패해도 조회 응답과 트랜잭션에 영향이 없음, dedup으로 차단된 재조회는 기존 동작 그대로
- 포트 계약 (Redis 컨테이너): 기록 후 포함 여부 true, 상한 초과 시 오래된 것부터 제거, TTL 설정, 같은 기록 중복 기록이 멱등, 키가 없으면 콜드 상태로 구분됨
- API / 통합: 조회 API 호출 뒤 같은 사용자의 피드에서 그 기록이 빠짐(다른 사용자는 유지), 비회원도 동일, seen-set 키를 지운 뒤에도 DB 이력으로 복구되어 여전히 제외됨, 내 기록 제외와 함께 동작
- 경계값 / 예외: 상한(1,000건)을 넘으면 가장 오래된 조회가 다시 노출됨 (알려진 한계로 테스트에 명시), 로그인 시 비회원 이력이 사용자로 병합된 경우 병합된 행이 웜업에 포함됨

### S-4 전역 점수 랭킹 피드 (윤곽, 착수 전 구체화)

- 방향: 같은 엔드포인트에 정렬 옵션으로 추가(기본은 최신순 유지). 후보는 최근 공개 기록 M개(설정값), 점수는 좋아요·조회수와 시간 감쇠로 계산해 정렬. 페이지 위치는 cursor에 담고 점수 변동에 의한 소량 중복·누락은 허용. 점수는 응답에 노출하지 않는다
- 테스트 윤곽: 점수가 높은 기록이 앞서는지, 같은 점수에서 결정적 순서, 시간 감쇠, 비로그인 동작, 최신순 옵션이 S-1과 같은 결과, 응답에 점수 필드가 없음

### S-5 개인 가중 (윤곽, 착수 전 구체화)

- 방향: 팔로우한 작성자, 사용자가 최근 좋아요·조회한 기록의 타입·태그·감정 빈도로 가중. 신호가 없으면(콜드 스타트, 비로그인) 가중 없이 S-4와 같음
- 테스트 윤곽: 가중이 순서를 바꾸는지, 신호 없음이 S-4와 동일, 가중에 쓰는 데이터 조회 상한, 팔로우 해제 반영

### S-6 사전 점수 계산과 스냅샷 (윤곽, 착수 전 구체화)

- 방향: 전역 점수를 Redis ZSET에 주기적으로(그리고 새 기록 이벤트로) 갱신하고, 요청 시 상위 후보를 읽어 개인 가중과 seen 필터를 적용한다. 첫 요청에서 후보 순서를 스냅샷으로 저장하고 cursor가 스냅샷과 위치를 가리켜 페이지 일관성을 보장
- 테스트 윤곽: 스냅샷 범위에서 페이지 간 중복·누락 0, 스냅샷 만료 시 동작, 갱신 잡의 멱등성, 점수 갱신이 지연되어도 피드가 응답함
- 갱신 잡을 여러 인스턴스가 실행할 때의 처리는 수평 확장 ADR과 함께 정한다

## 위험도와 리뷰 깊이

| # | 위험도 | 근거 | 정독 지점 |
|---|---|---|---|
| S-1 | 중간 | 새 조회 쿼리와 공개 API. 데이터 변경은 없다 | 쿼리 조건(비공개·삭제·탈퇴 작성자·내 기록)과 cursor 검증이 노출 정책과 일치하는지 |
| S-2 | 높음 | 운영 테이블에 대한 마이그레이션(인덱스) 가능성 | 마이그레이션 SQL, 인덱스 컬럼 순서와 쿼리 조건·정렬의 대응, 성능 단언이 실제 읽은 행을 측정하는지 |
| S-3 | 높음 | Redis 정합성·동시성과 조회 쓰기 경로 변경 | `RecordViewService`의 커밋 후 처리에서 seen 기록 실패가 조회 결과에 영향이 없는지, 웜업의 동시 실행과 표식, 스캔 루프의 종료 조건과 cursor 의미 |
| S-4 | 중간 | 정렬 로직 추가. 저장소 변경 없음 | 점수 공식의 경계값(조회수 0, 오래된 기록) |
| S-5 | 중간 | 개인 신호 조회가 요청 경로에 추가됨 | 신호 조회의 상한과 실패 시 S-4로의 대체 |
| S-6 | 높음 | 사전 계산과 스냅샷의 정합성, 잡의 다중 인스턴스 실행 | 스냅샷 키와 TTL, 갱신 잡의 멱등성과 중복 실행 |

## 끝단 검증

자동화된 시나리오로 정의하며 수동 확인으로 대체하지 않는다.

- 사용자 A, B와 B의 공개·비공개·삭제 기록으로, A의 로그인 피드를 cursor로 끝까지 순회하면 공개 기록만 정확히 한 번씩 나오고 A의 기록은 없다
- A가 일부 기록을 조회한 뒤 다시 순회하면 조회한 기록은 나오지 않는다. 비로그인(비회원) 순회도 같다
- 대량 시드 성능 검증(S-2)은 CI 실행 시간에 미치는 영향을 확인한 뒤 일반 테스트로 둘지 별도 태그로 분리할지 정한다

## 비범위

- 팔로우한 사용자 기록만 모아 보는 타임라인(별도 기능)
- 피드 항목의 광고·알림 삽입, 신고·차단, 사용자 선택 필터(타입·태그)
- 인기 점수 기반 검색, 기존 `GET /records` 목록 API의 변경(offset 방식 유지)
- `record_views` 테이블 주석(V8)의 정정: 이미 적용된 마이그레이션이라 수정할 수 없고, 정정하려면 주석을 바꾸는 마이그레이션이 새로 필요하다
- 비회원이 로그인할 때 seen-set 병합(`record_views`는 병합되므로 콜드 시 웜업으로 반영된다)
- 다중 인스턴스에서의 갱신 잡 조정 (수평 확장 ADR)

## 열린 질문

2·3단계의 구체값은 1단계의 실측 결과를 보고 정해야 하므로 지금 확정하지 않는다. 각 항목은 해당 슬라이스 착수 전에 이 문서를 갱신해 닫는다.

- (S-2) 인덱스가 필요한지, 시드 비율과 읽은 행 수의 상한값, 쿼리 수 상한: 대량 시드 측정 결과가 있어야 정할 수 있다
- (S-3) seen-set의 상한(제안 1,000건)과 TTL(제안 30일), 스캔 라운드 상한과 배치 크기: 실제 조회 패턴 없이 정한 초기값이라 구현 후 조정한다
- (S-4) 점수 공식의 형태와 가중치, 후보 윈도우 크기, 정렬 옵션의 API 형태: 1단계 데이터 분포를 본 뒤 정한다
- (S-5) 개인 가중에 쓸 신호의 종류와 비중, 신호 조회 방식(요청 시 계산 / 캐시): S-4 결과를 본 뒤 정한다
- (S-6) 갱신 주기와 방식(스케줄러 / 이벤트), 스냅샷 TTL, 갱신 잡의 실행 주체: 수평 확장 ADR과 함께 정한다
