# 기록 피드 (최신순 cursor → 점수 → 사전 계산)

- 상태: 초안
- 작성일: 2026-10-29
- 관련: [모듈·패키지·의존 구조 ADR](../../decisions/module-and-package-structure.md), 수평 확장 ADR(작성 전, 3단계 슬라이스와 함께 결정)

---

## 배경과 목표

기록을 한곳에서 이어서 볼 수 있는 피드를 만든다. 대형 트래픽 서비스에 실제로 도입한다는 전제로, 한 번에 완성하지 않고 단계별로 키운다.

1. **최신순 + cursor 페이징**: 공개 기록 전체를 최신순으로, 깊은 페이지에서도 비용이 일정하게
2. **점수 도입**: 전역 점수(좋아요·조회·시간 감쇠) → 사용자별 개인 가중
3. **사전 점수 계산**: 점수를 미리 계산해 두고, 스냅샷으로 페이지 일관성을 확보

끝나면 다음이 가능해진다.
- 비로그인과 로그인 사용자 모두 피드를 받는다. 로그인 사용자는 내가 쓴 기록과 이미 조회한 기록을 제외한 피드를 본다.
- 기록 수가 늘어도 피드 조회 비용이 페이지 깊이와 무관하다.
- 이후 단계가 같은 엔드포인트와 패키지 위에서 점수와 사전 계산을 얹는다.

**진행 방식**: 문서 하나로 간다. 1단계(S-1~S-3)는 슬라이스와 테스트 케이스를 확정하고, 2·3단계(S-4~S-6)는 방향과 윤곽만 적는다. 설계가 바뀌면 코드보다 문서를 먼저 고치고, 2·3단계는 착수 전에 이 문서의 해당 슬라이스를 구체화한다.

## 결정 사항

| 결정 | 선택 | 대안 | 선택 이유 |
|---|---|---|---|
| 정렬과 cursor | `id DESC`. cursor는 마지막으로 **스캔한** 기록 id를 불투명 문자열(Base64)로 인코딩 | `created_at + id` 복합 cursor / offset | PK는 단조 증가하고 유일해서 동률이 없고 PK 인덱스만으로 조회된다. offset은 깊어질수록 읽는 행이 늘고, 도중에 기록이 등록되면 중복·누락이 생긴다. 새 기록은 더 큰 id라 이미 받은 페이지 뒤쪽에 영향이 없다 |
| 응답 형식 | `data`와 `nextCursor`(마지막 페이지면 null). `totalCount` 없음 | `totalCount` 포함 / `hasNext` 불리언 | 전체 개수 `COUNT`는 피드에서 쓸모가 없고 비용만 든다. `nextCursor`가 `hasNext`를 겸한다. 한 건 더 조회(`size+1`)로 다음 페이지 유무를 판단한다 |
| 메서드 이름 | 서비스와 저장소 모두 `searchRecordFeeds(...)` | 서비스 `searchRecordFeeds`, 저장소 `searchFeedRecords` / `fetchRecordFeed` | 이 코드베이스는 서비스와 저장소가 같은 이름을 쓴다(`searchRecords`, `searchSubjects`, `searchEmotions`, `searchNotifications`). 호출 흐름에서 이름이 이어지고 검색하기 쉽다. "피드 항목 하나"를 `RecordFeed`로 보면 `searchRecordFeeds`는 `searchRecords`와 같은 규칙이다. 저장소가 `Record` 엔티티를 반환하는 점은 `searchRecords`도 같다 |
| cursor 인코딩 | 정책을 담은 범용 `UrlSafeBase64`(`api/common/web`, `object`)를 쓴다. 인코딩은 URL 안전 알파벳·패딩 없음·UTF-8, 디코딩은 URL 디코더로 엄격하게 하고 실패하면 `null`을 돌려준다. 기록 id 해석 규칙(`parseCursor`)은 `RecordFeedConverter`에 한 곳으로 두고, 검증기가 이를 써서 `INVALID_FEED_CURSOR`를 던진다 | cursor 전용 코덱 / 호출 지점에서 `java.util.Base64`를 직접 사용 | cursor는 응답으로 내려간 뒤 쿼리 파라미터로 되돌아오는 값이다. 정책(알파벳·패딩·문자셋)이 호출 지점마다 흩어지면 일관성이 깨지고, 출력이 URL의 unreserved 문자(`A-Z a-z 0-9 - _`)뿐이면 어떤 위치에서도 퍼센트 인코딩이 필요 없다. 현재 payload(숫자)는 Basic으로도 `+`·`/`가 나오지 않지만 S-4·S-6의 cursor는 숫자만 담지 않을 수 있어 처음부터 못 박는다. `common`의 역할 목록에 `util`은 없으므로 정책의 성격(웹 계약)에 맞는 `common/web`에 둔다. 디코더는 깨진 입력을 예외로 드러내는 URL 디코더를 쓴다(MIME 디코더는 깨진 입력도 빈 값으로 통과시킨다) |
| 요청 변환과 검증 | 요청 DTO는 데이터만 갖는다. `RecordFeedConverter`가 검증된 요청을 조회 조건(`RecordFeedQueryFilter`)으로 바꾸고 cursor 해석 규칙(`parseCursor`)을 한 곳에 둔다. 검증기는 같은 `parseCursor`로 유효성만 판단해 에러 코드를 정한다. `size+1` 조회와 `nextCursor` 계산은 서비스에 둔다 | DTO 파생 프로퍼티 / 검증기가 DTO 필드를 채움 / 검증 결과를 타입으로 반환(`Validated...`) / 서비스가 직접 조건을 조립 | 기존 `searchRecords`가 `recordConverter.convert(request)`로 요청을 조회 조건으로 바꾸는 패턴을 따른다. 해석 규칙이 검증과 변환에 두 번 필요하지만 한 함수로 단일화된다. 검증기를 통과한 요청만 컨버터에 도달하므로 컨버터의 `!!`는 도달 불가능한 분기다(기존 `request.userId!!` 선례). 검증 결과를 타입으로 돌려주는 방식은 검증기 전체의 컨벤션 변경이라 별도로 논의한다. `size+1` 읽기와 자르기는 한 기법의 두 반쪽이라 갈라 두면 한쪽 변경이 다른 쪽을 조용히 깨뜨리므로 모두 서비스에 둔다 |
| 응답 항목 타입 | 기존 `RecordResponse` 재사용 | 처음부터 `RecordFeedResponse`로 분리 | S-1~S-4까지 `RecordResponse`와 달라질 필드가 확정된 것이 없다. 피드 전용 필드(예: 노출 이유)가 실제로 필요해지면 `api/record/feed` 안에서 분리한다. 소비자가 피드 컨트롤러 하나뿐이라 분리 비용이 작다 |
| 점수 노출 | 점수는 응답에 노출하지 않는다 | 점수를 응답에 포함 | 점수는 서버 내부의 랭킹 구현이다. 노출하면 공식을 바꿀 때마다 API 계약이 흔들리고, 클라이언트는 순서만 필요하다 |
| 페이지 크기 | 기본 20, 최대 50 | 상한 없음 | 한 요청이 읽는 행과 Redis 배치 조회를 제한한다 |
| 엔드포인트 | `GET /api/v1/records/feed` | `GET /api/v1/feeds/records` | 기록 도메인의 피드이고 새 최상위 기능 패키지(ArchUnit 허용 목록 수정)가 필요 없다. `/records/{id}`와 경로가 겹치지만 리터럴이 우선하며 테스트로 고정한다 |
| 패키지 | `api/record/feed/{controller,service,dto,validator,converter}`. `domain`에는 새 패키지 없음 | 기존 `api/record/` 레이어에 추가 | 피드는 엔티티·리포지토리가 없는 읽기 모델이라 `domain` 서브 도메인이 아니다. 2·3단계에서 점수·스냅샷·스케줄러 클래스가 늘어나므로 `RecordService`와 분리한다. 조회 메서드는 `RecordRepository`에 추가한다 |
| 비로그인 | 허용 (전역 피드). 보안 설정은 `/api/**` 전체가 `permitAll`이라 변경 없음 | 로그인 전용 | 기존 기록 목록도 비인증 공개이고, 이후 개인화가 없는 사용자의 기본 경로가 된다 |
| 노출 정책 | 항상 제외: 비공개, 삭제, **탈퇴(`resigned`) 작성자**의 기록. 로그인 시 추가 제외: 내가 쓴 기록. **공개 `DIARY`는 포함** | `DIARY` 제외 / 탈퇴 작성자 노출 | 기존 목록은 탈퇴 작성자 기록도 노출하지만 피드는 제외한다(단건·목록 동작은 바꾸지 않는다). `DIARY` 제외는 선택되지 않았다 |
| 조회한 기록 제외 | Redis seen-set을 **캐시**로 쓰고, 원천은 DB(`record_views`). seen-set이 비어 있으면 DB에서 최근 조회를 읽어 채운다 (S-3) | 피드 쿼리에서 DB `NOT EXISTS` / 2단계로 미룸 | `record_views`는 조회 요청 트랜잭션에서 동기로 저장되므로 DB는 항상 정확하다. 다만 append-only로 계속 커지는 테이블에 피드 요청마다 `NOT EXISTS`를 거는 것은 대형 트래픽 전제에 맞지 않는다. 좋아요·조회수와 같은 "캐시 + 원천에서 복구" 구조를 따른다 |
| seen-set 포트 | 기록 전용 `RecordSeenProvider`를 `domain/record/provider`에 정의, 구현은 `infrastructure/redis` | `CacheProvider`에 집합 연산 추가 | `CacheProvider`는 문자열 연산 포트로 단순하다. ZSET 연산과 상한·TTL 정책을 거기에 섞지 않는다. ADR 002의 "구현 기술은 `domain`의 포트를 통해서만 쓴다"를 따른다 |
| seen-set 쓰기 규칙 | `markSeen`은 seen-set이 **이미 있을 때만** 쓴다(없으면 건너뜀, Lua로 존재 확인과 쓰기를 원자 처리). 웜업(`warm`)만 키를 만든다 | 키가 없어도 쓴다 | 웜업 전에 `markSeen`이 키를 만들면 일부만 든 불완전한 집합이 "웜" 상태로 보여 이전에 본 기록이 TTL 동안 다시 노출된다. 건너뛰어도 안전한 이유는 `record_views`가 조회와 같은 트랜잭션에서 커밋되므로 다음 피드 요청의 웜업이 이 조회를 포함하기 때문이다 |
| 웜업 순서(경합 방지) | 웜업은 **표식을 먼저 만든 뒤(`beginWarm`) DB 이력을 읽는다.** `beginWarm`은 표식 멤버만 든 집합을 짧은 TTL로 만들고(이미 있으면 아무것도 하지 않음), 이어서 `warm`이 이력을 채우고 TTL을 늘린다 | DB를 읽은 뒤 키를 만듦 / 키 생성 후 DB를 한 번 더 읽음 | `markSeen`은 키가 없으면 건너뛰므로, DB를 읽은 직후 조회가 커밋되고 `markSeen`이 키 생성 전에 실행되면 그 조회가 빠진 채로 키가 만들어져 30일 동안 걸러지지 않는다(코드 리뷰에서 지적). 표식을 먼저 만들면 표식 이후의 `markSeen`은 키를 만나 반영되고, 표식 이전에 커밋된 조회는 DB 읽기에 포함되므로 추가 쿼리 없이 경합이 닫힌다. 대가: 채우는 몇 ms 동안 같은 조회자의 다른 요청이 덜 채워진 집합을 볼 수 있고, DB 읽기가 실패하면 10분짜리 표식만 남는다(둘 다 일시적) |
| 신규 비회원 식별자 | `GuestIdAssignFilter`가 **방금 발급한** 식별자는 요청 속성(`GUEST_ID_ISSUED`)으로 표시하고, 피드는 이를 조회자 없음으로 처리해 조회 제외를 건너뛴다. 조회 API가 식별자를 기록하는 동작은 그대로다 | 모든 새 식별자에 웜업 / 키만 짧게 | 새로 발급된 식별자는 이력이 있을 수 없다. 쿠키 없이 반복 요청하는 크롤러는 요청마다 새 식별자를 받아 DB 쿼리와 Redis 키가 요청률에 비례해 생겼다(코드 리뷰에서 지적). 건너뛰면 이 경로의 비용이 S-3 이전과 같아진다. 쿠키를 돌려보내는 방문자는 두 번째 요청부터 조회 제외를 받는다 |
| 이력 없는 조회자의 표식 키 | 조회 이력이 없는 웜업은 **짧은 TTL(10분)** 로 만들고, 이미 있는 집합의 만료는 줄이지 않는다. 조회가 기록되면(`markSeen`) 30일로 늘어난다 | 모든 표식 키를 30일로 | `GuestIdAssignFilter`가 쿠키 없는 모든 요청에 새 비회원 식별자를 발급하고 피드는 공개 API라서, 쿠키 없이 반복 요청하는 크롤러는 요청마다 새 조회자가 되어 표식 키가 요청률에 비례해 30일 동안 쌓인다. 짧은 TTL이면 키의 양이 요청률 × 10분으로 제한되고, 같은 쿠키로 다시 오는 사용자는 DB를 다시 치지 않는다 |
| 조회자 식별 | 회원이 우선이고 없으면 비회원 식별자. `RecordViewer`(`domain/record/view/vo`)가 키 규칙(`user:{id}` / `guest:{id}`)을 한곳에서 만들고 조회 이력, 조회 중복 방지, 피드가 같이 쓴다 | 서비스마다 인라인으로 조립 | 조회 시 쓰는 키와 피드가 확인하는 키가 달라지면 본 기록이 걸러지지 않는다. 한곳에 두어 어긋남을 막는다 |
| seen 확인 방식 | 후보 id만 `ZMSCORE`로 확인한다(Redis 6.2 이상). 키가 없으면 콜드로 구분한다 | 매 요청 전체 집합(최대 1,000건) 조회 / 후보별 `ZSCORE` | 전체 집합을 읽으면 요청마다 약 8KB를 옮긴다. 운영 Redis가 6.2 미만이면 파이프라인 `ZSCORE`로 바꿀 수 있고 포트 뒤에 숨겨져 호출부는 달라지지 않는다 |
| 스캔·cursor 규칙 | 첫 라운드는 `size`건, 이후 라운드는 부족한 수의 2배, 최대 3라운드. cursor는 정확히 `size`개를 채웠으면 마지막 응답 기록 id(채운 지점 뒤에 읽을 기록이 없고 배치에 남은 후보가 모두 본 기록이면 null), 라운드가 소진됐으면 스캔한 마지막 id | 첫 라운드부터 2배 / 라운드 제한 없음 | 본 기록이 적은 대부분의 요청은 1라운드로 끝나 S-1과 같은 비용이다. 배치 중간에서 끊을 때는 이후 기록이 다음 요청에서 다시 스캔되어 누락이 없다. 본 기록이 많으면 응답이 `size`보다 짧거나 비어도 `nextCursor`가 있을 수 있고, 클라이언트는 `nextCursor`가 있는 동안 계속 요청한다 |
| 인덱스 | **추가하지 않는다** (S-2 측정 결과) | 복합 인덱스 `(is_deleted, is_private, id)` | 20만 건(공개 70%, 비공개 15%, 삭제 15%, 탈퇴 작성자 포함)에서 PK 역방향 범위 스캔만으로 반환 1건당 약 4행을 읽고, cursor 위치(남은 기록 0.1%~90%)와 무관하다. 복합 인덱스를 만들어도 옵티마이저는 PK를 그대로 고르고, `FORCE INDEX`로 강제해도 읽은 행이 54에서 42로 줄 뿐이라 운영 테이블 마이그레이션과 모든 `INSERT`의 쓰기 비용을 감수할 이득이 없다. 읽는 행은 대략 `반환 수 / 노출 비율`에 비례하므로 노출 비율이 1%대로 떨어질 때 다시 본다 |
| 성능 검증 | 읽은 행 수(`Handler_read_*`)와 실행 계획(`EXPLAIN`)으로 단언하고, 시간은 로그로만 남긴다 | 처리 시간 임계값 단언 / k6 부하 테스트 | 시간 단언은 환경에 따라 흔들린다. 부하 테스트는 이 슬라이스 범위에 넣지 않는다 |
| 피드 조회 쿼리 구조 | 두 번에 나눠 조회한다(deferred join). ① 필터·정렬·limit은 id만 뽑는 쿼리, ② 그 id의 기록을 리뷰·감정과 함께 `fetch join` | 한 쿼리에 `fetch join` / 지연 로딩에 맡김 | 리뷰·감정은 역방향 `OneToOne`이라 `fetch = LAZY`를 줘도 지연 로딩되지 않고 기록마다 추가 쿼리가 나간다(N+1, 측정: `2 × (size+1) + 7`개). 한 쿼리에 `fetch join`을 합치면 쿼리 수는 상수가 되지만 조인 순서가 바뀌어 첫 페이지가 `type=ALL`·`Using filesort`·읽은 행 340,009로 뒤집힌 것을 성능 테스트가 잡았다. id만 뽑는 쿼리는 안정적인 계획을 유지하고 두 번째 쿼리는 PK 조회 몇십 건이라 조인 순서가 바뀔 여지가 없다 |
| 조회수 카운터 일괄 조회 | `RecordViewQueryService.fetchViewCounts`를 좋아요 카운터처럼 `mget` 한 번으로 읽는다. 없는 키만 DB 조회 이력 수로 시드한 뒤 다시 읽는다(기존 의미 유지) | 기록마다 `hasKey`+`get` | 기록마다 Redis를 두 번 부르면 한 페이지에 `2 × size + 1`번 왕복한다. 공유 코드라 기존 목록 API(`searchRecords`)도 같이 개선되고, 결과는 동일하다 |
| 점수 순서 | 전역 점수(S-4) → 개인 가중(S-5) | 처음부터 사용자별 점수 | 전역 점수는 사용자와 무관해서 3단계 사전 계산이 단순하다. 개인 가중은 그 위에 요청 시점에 더한다 |
| 페이지 일관성 | 2단계는 best-effort(점수 변동으로 인한 소량 중복·누락 허용), 3단계 스냅샷으로 해결 | 2단계부터 일관성 보장 | 요청마다 점수를 고정하려면 사실상 스냅샷이 필요해 3단계 작업이 당겨진다. 3단계가 필요한 이유가 분명해진다 |

**새로 만든다 (S-1)**

- `api/record/feed/validator/RecordFeedParameterValidator`: `size` 범위와 cursor 형식. `@QueryObject`는 Bean Validation을 타지 않으므로 검증기에서 한다
- `api/record/feed/converter/RecordFeedConverter`: `parseCursor`(cursor → 기록 id, 해석 불가면 null), `convert`(검증된 요청 → `RecordFeedQueryFilter`), `convertToCursor`(기록 id → cursor)
- `api/common/web/UrlSafeBase64`: URL 안전 Base64 인코딩 정책(알파벳·패딩·문자셋)을 담은 범용 유틸
- `domain/record/vo/RecordFeedQueryFilter`: `beforeRecordId`, `excludeWriterId`
- `RecordRepository.searchRecordFeeds(...)`(반환: `Record` 엔티티 목록)와 `infrastructure`의 Adapter·`RecordQuerydslRepository` 구현
- `RecordErrorCode`에 `INVALID_FEED_CURSOR`(`INVALID`) 추가

**새로 만든다 (S-3)**
- `domain/record/provider/RecordSeenProvider`(포트), `domain/record/vo/RecordFeedRedisKey`
- `infrastructure/redis`의 구현(`RedisRecordSeenProvider`). Redis 키는 `record-feed:seen:{viewerKey}:v1` ZSET(점수=조회 시각, 멤버=기록 id), 상한 1,000건·TTL 30일은 `RecordFeedRedisKey`의 상수. 조회자 키(`viewerKey`)는 `RecordViewService`가 쓰는 `user:{id}` / `guest:{id}` 형식을 그대로 쓴다. 포트는 `findSeen`(키가 없으면 null, 있으면 후보 중 본 기록 id), `markSeen`(키가 있을 때만 기록), `beginWarm`(DB를 읽기 전에 표식만 든 집합을 짧은 TTL로 만든다), `warm`(DB 이력으로 채우고 이력이 있으면 TTL을 늘림, 이력이 없어도 표식 멤버가 남아 키가 생김)
- `domain/record/view/vo/RecordViewer`: 조회자(회원/비회원)와 조회자 키
- `api/common/security/GuestIdAssignFilter`(발급 시 `GUEST_ID_ISSUED` 표시)와 `api/common/web`의 `@ReturningGuestId` 해석기: 피드가 방금 발급된 비회원 식별자를 걸러 낸다
- `api/record/feed/service/RecordFeedSeenService`: 요청마다 `finderFor(viewer)`로 만든 finder가 후보 중 본 기록을 돌려준다. 콜드면 DB 이력으로 한 번만 웜업하고, 저장소가 실패하면 그 요청에서는 필터 없이 응답한다. 피드 컨트롤러가 `@GuestId`를 받는다(비회원도 조회 제외를 받는다)
- `RecordViewRepository`에 사용자별·비회원별 최근 조회 기록 id 조회 추가 (웜업용, 기록별 가장 최근 조회 순으로 상한 건수)

**바뀐다**
- S-3: `RecordViewService.recordView`가 커밋 후 seen-set에 기록한다(조회수 반영 뒤에, 실패를 삼키는 별도 처리). 조회자 키는 `RecordViewer`로 만든다. 기존 조회수·dedup 흐름은 그대로 둔다. `RecordFeedService.searchRecordFeeds`는 비회원 식별자를 받아 스캔 루프를 돌린다
- S-2: `RecordQuerydslRepository.searchFeedByFilter`를 두 번 조회(deferred join)로 바꾼다. `RecordViewQueryService.fetchViewCounts`를 `mget`으로 바꾼다(공유 코드, 기존 목록 API도 영향). **마이그레이션은 없다**

**건드리지 않는 외부 계약**: 기존 기록 API(목록·단건·등록·수정·삭제·조회수), DB 스키마의 컬럼, 이벤트 페이로드, Redis 기존 키.

**알고 있는 사실 (코드로 확인)**
- `record_views`는 조회 요청의 같은 트랜잭션에서 저장된다. Kafka·Outbox는 Redis 조회수 카운터를 재동기화하는 부가 경로다.
- `V8__add_record_views_table.sql`의 테이블 주석은 "Kafka를 거쳐 쌓인다"고 적혀 있어 구현과 다르다. 이 설계는 코드를 기준으로 한다. 주석 정정은 비범위에 적었다.
- `idx_record_views_user_id`는 InnoDB 보조 인덱스라 PK(`id`)를 포함한다. 사용자별 최근 조회를 `id` 역순으로 읽는 웜업 쿼리가 인덱스를 탈 수 있다.

## 슬라이스별 테스트 케이스

구현 전에 이 목록을 확정하고, 테스트를 먼저 작성해 실패를 확인한 뒤 구현한다.

### S-1 공개 기록 최신순 cursor 피드 API

- 단위 (서비스, Kotest `BehaviorSpec` + MockK):
  - cursor가 없으면 첫 페이지: 저장소에서 `size+1`건을 읽고, 초과분이 있으면 응답은 `size`건과 `nextCursor`(마지막 응답 기록 id)
  - 결과가 `size` 이하면 `nextCursor`가 null, 결과가 0건이면 `data`가 비고 `nextCursor`가 null
  - 로그인 사용자의 id가 `excludeWriterId`로, 비로그인은 null로 전달됨
  - 좋아요·조회수는 응답 기록 id 목록으로 배치 조회 1회씩
- 단위 (컨버터): `convertToCursor`↔`parseCursor` 왕복, 숫자가 아닌 값·0·음수·Long 범위 초과·깨진 Base64는 `parseCursor`가 null, `convert`가 cursor를 `beforeRecordId`로, 요청자 id를 `excludeWriterId`로 옮김(cursor 없음·비로그인은 null)
- 단위 (검증기): 깨진 cursor는 `INVALID_FEED_CURSOR`(위 깨진 입력 전부), 유효한 cursor는 통과
- 단위 (`UrlSafeBase64`): 한글·구분 기호가 섞인 값까지 왕복, 표준 `Base64`라면 `+`·`/`·`=`가 나오는 값에서 출력이 `A-Z a-z 0-9 - _`뿐이고 패딩이 없음, 패딩이 붙은 입력도 해석, 알파벳 밖 문자·표준 알파벳 문자·UTF-8이 아닌 바이트는 `null`
- 단위 (검증기): `size`가 1 미만이거나 50 초과면 400
- 저장소 계약 (MySQL 컨테이너): `id DESC` 정렬, `id < cursor` 조건, 비공개 제외, 삭제 제외, 탈퇴 작성자 제외, `excludeWriterId` 제외, 공개 `DIARY` 포함, `limit` 적용
- API / 통합:
  - 비로그인 요청이 200
  - 로그인 요청에서 내 기록이 빠짐
  - 기록 45건(공개), `size=20`으로 `nextCursor`를 따라가면 20·20·5건이고 합집합이 전체와 같으며 중복이 없음
  - 순회 도중 새 기록이 등록되어도 이미 받은 페이지와 다음 페이지에 중복·누락이 없음
  - `/records/feed`가 `/records/{id}`로 라우팅되지 않고 `/records/{숫자}`는 기존대로 단건 조회
- 경계값 / 예외: `size=1`, `size=50`, `size=51`(400), 존재하는 최대 id보다 큰 cursor(첫 페이지와 같은 결과), 가장 작은 id를 가리키는 cursor(빈 결과), 기록이 0건

### S-2 대량 시드 성능 검증과 쿼리 수 상수화

측정 결과(구현 후, MySQL 8.0 컨테이너, 시드 약 2.5초):

| 항목 | 측정 |
|---|---|
| 시드 | 기록 200,000건(공개 70%, 비공개 15%, 삭제 15%), 작성자 105명(탈퇴 5명). 피드 노출 133,336건 |
| 첫 페이지(`limit` 21) 읽은 행 | 82, 로그인(본인 제외)도 82. 반환 1건당 약 3.9행 |
| `size=50` 첫 페이지(`limit` 51) | 184 (1건당 약 3.6행) |
| cursor 아래 남은 기록 0.1%~90% | 81~91, 계획은 모두 PK `range`, filesort 없음 |
| 같은 깊이의 offset 쿼리(page=5000) | 200,043 (cursor 방식의 약 2,400배) |
| DB 쿼리 수(캐시가 따뜻할 때) | `size` 5·20·50 모두 8개(기록 2 + 작성자·태그·리뷰 주제·주제 이미지·감정·감정 카테고리 배치 6). 수정 전 `2 × (size+1) + 7` |
| Redis 명령 수(캐시가 따뜻할 때) | `size`와 무관하게 2개(좋아요 `mget` 1 + 조회수 `mget` 1). 수정 전 `2 × size + 1` |

- 단위 (`RecordViewQueryService.fetchViewCounts`): 모두 캐시에 있으면 `mget` 한 번만 쓰고 `hasKey`·`get`·DB를 부르지 않음, 일부가 없으면(cold start) 없는 기록만 DB 조회 이력 수로 시드하고 나머지는 캐시 값 사용, 시드하는 사이 다른 요청이 카운터를 올렸으면(`putIfAbsent` 실패) 시드 값이 아니라 캐시의 최신 값을 반환, 빈 목록은 빈 맵
- 저장소 계약: 위 S-1 케이스가 두 번 조회 구조에서도 그대로 통과(정렬·cursor 경계·노출 정책)
- 성능 (`RecordFeedPerformanceTest`, 시드 직후 `ANALYZE TABLE` 필수): 첫 페이지·로그인·`size=50`·cursor 위치별(남은 0.1%, 1%, 10%, 50%, 90%)에서 `records` 접근이 `ALL`이 아니고 `Using filesort`가 없으며 읽은 행이 `limit × 8` 이하, 깊은 페이지 읽은 행이 첫 페이지의 2배 이하. 시간은 단언하지 않는다. offset 대조는 로그만 남긴다
- 쿼리 수 (`RecordFeedQueryCountTest`, 전체 컨텍스트): 캐시가 따뜻할 때 `size=5`와 `size=50`의 DB 쿼리 수가 같고 10개 이하, Redis 명령 수가 같고 3개 이하. 콜드 캐시는 알려진 한계라 단언하지 않고 출력만 한다
- 변이 검증으로 단언이 실제로 잡는지 확인: 리뷰·감정 `fetch join` 제거, `mget`을 기록별 `hasKey`/`get`으로 되돌림, 시드 후 재조회 생략, 정렬을 `created_at`으로 변경, `limit` 제거, 한 쿼리에 `fetch join` 합치기(첫 페이지 `ALL`·filesort로 실패)

### S-3 조회한 기록 제외

구현 결과 측정(S-2의 쿼리 수 테스트 환경, 캐시가 따뜻한 상태):

| 방문자 | DB 쿼리 | Redis 명령 | 비고 |
|---|---|---|---|
| 재방문자(같은 쿠키, seen-set 있음) | 8 (S-3 이전과 같음) | 4 (카운터 `mget` 2 + 존재 확인 1 + 후보 점수 조회 1) | `size` 5·50 모두 같음 |
| 첫 방문자(요청마다 새 쿠키, 콜드 웜업) | 9 (`record_views` 최근 이력 조회 1 추가) | 10 | `size`와 무관한 고정 비용 |


- 단위 (서비스):
  - seen에 있는 기록은 응답에서 빠지고, 빠진 만큼 추가로 스캔해 `size`를 채움
  - 스캔 라운드 상한에 도달하면 부분 페이지와 `nextCursor`(스캔한 마지막 id)를 반환
  - 스캔한 후보가 모두 seen이어도 끝이 아니면 `data`가 비고 `nextCursor`가 있음
  - 스캔 결과가 배치보다 적으면 끝이므로 `nextCursor`가 null
  - seen 조회(Redis)가 실패하면 필터 없이 응답함 (피드는 가용성 우선)
  - 비회원은 `guestId`로, 식별자가 없는 요청은 제외 필터를 적용하지 않음
  - 첫 라운드는 `size`건, 본 기록이 있으면 이후 라운드는 부족한 수의 2배를 읽고 최대 3라운드에서 멈춤
  - 한 배치 중간에서 `size`개가 채워지면 cursor는 마지막 응답 기록 id(이후 기록은 다음 요청에서 다시 스캔됨)
  - 한 요청에서 seen 확인은 라운드마다 하지만 웜업은 한 번만 함
  - 웜업은 표식 생성(`beginWarm`) → DB 이력 읽기 → 채우기(`warm`) 순서로 호출됨
  - 채운 지점 뒤에 배치 밖 기록이 없고 배치에 남은 후보가 모두 본 기록이면 cursor가 null(빈 마지막 페이지를 만들지 않음)
  - seen-set이 비어 있으면 DB 최근 조회로 웜업하고, 조회 이력이 없는 사용자는 표식을 남겨 매 요청 재웜업하지 않음
- 단위 (필터·인자 해석기): `GuestIdAssignFilter`는 식별자를 새로 발급할 때만 `GUEST_ID_ISSUED`를 표시함, 피드의 비회원 식별자 해석기는 쿠키로 받은 식별자만 돌려주고 방금 발급한 것은 null
- 단위 (컨버터·컨트롤러): 피드 컨트롤러가 쿠키로 받은 비회원 식별자를 서비스에 전달함, 조회자 키는 회원이 우선이고 없으면 비회원
- 단위 (`RecordViewService`): 조회 성공의 커밋 후에 seen-set 기록이 호출됨, seen 기록이 실패해도 조회 응답과 트랜잭션에 영향이 없음, dedup으로 차단된 재조회는 기존 동작 그대로
- 포트 계약 (Redis 컨테이너, 경합): `beginWarm`이 표식만 든 집합을 짧은 TTL로 만들고 이미 있는 집합은 건드리지 않음, `beginWarm` 이후의 `markSeen`은 반영되고(이후 `warm`이 와도 유지) 이전의 `markSeen`은 건너뜀
- 포트 계약 (Redis 컨테이너): **키가 없을 때 `markSeen`은 키를 만들지 않음**(불완전한 집합 방지), 웜업 후에는 `markSeen`이 반영됨, 웜업은 조회 이력이 없어도 키를 만들어 콜드와 구분됨, 웜업이 이미 있는 더 최근 점수를 덮어쓰지 않음, 후보 중 본 기록만 반환,
  기록 후 포함 여부 true, 상한 초과 시 오래된 것부터 제거, TTL 설정, 같은 기록 중복 기록이 멱등, 키가 없으면 콜드 상태로 구분됨
- API / 통합: 조회 API 호출 뒤 같은 사용자의 피드에서 그 기록이 빠짐(다른 사용자는 유지), 비회원도 동일, seen-set 키를 지운 뒤에도 DB 이력으로 복구되어 여전히 제외됨, 내 기록 제외와 함께 동작
- 경계값 / 예외: 상한(1,000건)을 넘으면 가장 오래된 조회가 다시 노출됨 (알려진 한계로 테스트에 명시), 로그인 시 비회원 이력이 사용자로 병합된 경우 병합된 행이 웜업에 포함됨

### S-4 전역 점수 랭킹 피드 (윤곽, 착수 전 구체화)

- 방향: 같은 엔드포인트에 정렬 옵션으로 추가(기본은 최신순 유지). 후보는 최근 공개 기록 M개(설정값), 점수는 좋아요·조회수와 시간 감쇠로 계산해 정렬. 페이지 위치는 cursor에 담고 점수 변동에 의한 소량 중복·누락은 허용. 점수는 응답에 노출하지 않는다
- 테스트 윤곽: 점수가 높은 기록이 앞서는지, 같은 점수에서 결정적 순서, 시간 감쇠, 비로그인 동작, 최신순 옵션이 S-1과 같은 결과, 응답에 점수 필드가 없음

### S-5 개인 가중 (윤곽, 착수 전 구체화)

- 방향: 팔로우한 작성자, 사용자가 최근 좋아요·조회한 기록의 타입·태그·감정 빈도로 가중. 신호가 없으면(콜드 스타트, 비로그인) 가중 없이 S-4와 같음
- 테스트 윤곽: 가중이 순서를 바꾸는지, 신호 없음이 S-4와 동일, 가중에 쓰는 데이터 조회 상한, 팔로우 해제 반영

### S-6 사전 점수 계산과 스냅샷 (윤곽, 착수 전 구체화)

- 방향: 전역 점수를 Redis ZSET에 주기적으로(그리고 새 기록 이벤트로) 갱신하고, 요청 시 상위 후보를 읽어 개인 가중과 seen 필터를 적용한다. 첫 요청에서 후보 순서를 스냅샷으로 저장하고 cursor가 스냅샷과 위치를 가리켜 페이지 일관성을 보장
- 테스트 윤곽: 스냅샷 범위에서 페이지 간 중복·누락 0, 스냅샷 만료 시 동작, 갱신 잡의 멱등성, 점수 갱신이 지연되어도 피드가 응답함
- 갱신 잡을 여러 인스턴스가 실행할 때의 처리는 수평 확장 ADR과 함께 정한다

## 끝단 검증

자동화된 시나리오로 정의하며 수동 확인으로 대체하지 않는다.

- 사용자 A, B와 B의 공개·비공개·삭제 기록으로, A의 로그인 피드를 cursor로 끝까지 순회하면 공개 기록만 정확히 한 번씩 나오고 A의 기록은 없다
- A가 일부 기록을 조회한 뒤 다시 순회하면 조회한 기록은 나오지 않는다. 비로그인(비회원) 순회도 같다
- 대량 시드 성능 검증(S-2)은 시드 약 2.5초, 단언 3개 약 1초라 CI 시간에 큰 영향이 없어 일반 테스트로 둔다

## 비범위

- 팔로우한 사용자 기록만 모아 보는 타임라인(별도 기능)
- 피드 항목의 광고·알림 삽입, 신고·차단, 사용자 선택 필터(타입·태그)
- 인기 점수 기반 검색, 기존 `GET /records` 목록 API의 변경(offset 방식 유지)
- `record_views` 테이블 주석(V8)의 정정: 이미 적용된 마이그레이션이라 수정할 수 없고, 정정하려면 주석을 바꾸는 마이그레이션이 새로 필요하다
- 비회원이 로그인할 때 seen-set 병합(`record_views`는 병합되므로 콜드 시 웜업으로 반영된다)
- 다중 인스턴스에서의 갱신 잡 조정 (수평 확장 ADR)

## 알려진 한계

- **콜드 캐시:** 카운터 키가 없는 기록마다 좋아요·조회수 `COUNT(*)` 쿼리가 하나씩 나간다. 캐시 미스가 있는 동안만 생기는 비용이라 S-2에서는 고치지 않았다(배치 `GROUP BY`로 바꾸는 것은 후속 후보).
- **옵티마이저 통계:** 계획이 `range`로 유지되는 것은 InnoDB 통계가 최신일 때다. 대량 적재(마이그레이션, 데이터 이관) 직후 통계가 낡으면 cursor가 끝 쪽일 때 전체 스캔으로 뒤집히는 것을 측정 중에 관찰했다. 적재 뒤에는 `ANALYZE TABLE`을 실행한다. cursor는 서명하지 않아서 누구나 작은 id로 위조할 수 있으므로, 통계가 낡은 구간에는 요청 한 번이 전체 스캔 비용을 낼 수 있다(정보 노출은 없다).
- **쿠키를 돌려보내지만 이력이 없는 방문자(S-3):** 첫 요청에 조회 이력 쿼리 1회와 웜업(표식 키 10분 TTL)이 한 번 든다. 쿠키 없이 반복 요청하는 클라이언트는 방금 발급된 식별자라 조회 제외를 건너뛰므로 이 비용이 없다.
- **seen-set의 한계:** 상한(1,000건)을 넘는 오래된 조회는 다시 노출될 수 있다. 웜업은 최근 이력을 상한의 두 배 행만 읽고 중복을 제거하므로, 같은 기록을 매우 자주 본 조회자는 상한보다 적게 채워질 수 있다. `ZMSCORE`를 쓰므로 운영 Redis는 6.2 이상이어야 한다(미만이면 파이프라인 `ZSCORE`로 포트 구현만 바꾼다).
- **인덱스 재검토 조건:** 피드에 노출되는 기록의 비율이 1%대로 낮아지면 읽는 행이 `반환 수 / 노출 비율`로 늘어나므로 복합 인덱스를 다시 검토한다.

## 열린 질문

2·3단계의 구체값은 1단계의 실측 결과를 보고 정해야 하므로 지금 확정하지 않는다. 각 항목은 해당 슬라이스 착수 전에 이 문서를 갱신해 닫는다.

- (S-3) 상한 1,000건·TTL 30일·이력 없는 표식 10분·스캔 라운드 3회·재스캔 2배: 실제 조회 패턴 없이 정한 초기값이라 운영 지표를 보고 조정한다. 운영 Redis 버전(6.2 이상 필요)은 배포 전에 확인한다
- (S-4) 점수 공식의 형태와 가중치, 후보 윈도우 크기, 정렬 옵션의 API 형태: 1단계 데이터 분포를 본 뒤 정한다
- (S-5) 개인 가중에 쓸 신호의 종류와 비중, 신호 조회 방식(요청 시 계산 / 캐시): S-4 결과를 본 뒤 정한다
- (S-6) 갱신 주기와 방식(스케줄러 / 이벤트), 스냅샷 TTL, 갱신 잡의 실행 주체: 수평 확장 ADR과 함께 정한다
