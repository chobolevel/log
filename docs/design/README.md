# 설계 문서

기능 단위 설계 문서를 둔다. PR에서 이 문서를 링크해 리뷰 기준으로 사용한다.

## 작성 방법

- 템플릿은 [`_template.md`](_template.md)다. 복사해서 `<기능-slug>.md`(소문자, 하이픈)로 저장한다.
- Claude Code에서는 `/design <기능 설명>`으로 인터뷰를 거쳐 같은 구조의 문서를 만든다. 직접 써도 된다.
- 한 문서에 슬라이스 분해(동작 변화 단위), 슬라이스별 테스트 케이스, 위험도, 끝단 검증을 포함한다.
- 구조 수준의 결정은 `decisions/`에 ADR로 남긴다. ADR과 설계 문서의 구분은 아래 "ADR과 설계 문서의 역할"을 따른다.
- 설계 문서는 구현 전에 확정한다. 구현 중 설계가 바뀌면 코드보다 문서를 먼저 고친다.

## ADR과 설계 문서의 역할

| | ADR (`decisions/`) | 설계 문서 (`docs/design/`) |
|---|---|---|
| 담는 것 | 되돌리기 어렵고 여러 기능에 걸치는 결정 (모듈 구조, 의존 방향, 인프라 선택 등) | 한 기능을 만드는 계획: 결정 사항 표, 영향 범위, 슬라이스, 슬라이스별 테스트 케이스 |
| 양식 | 상황 → 문제 → 대안 → 결정 → 결과 | [`_template.md`](_template.md) |
| 진행 상태 | 두지 않는다 (커밋 해시, 단계별 결과, "완료/예정" 표시 없음) | 상태와 슬라이스별 PR 링크를 둔다 |
| 결정이 바뀌면 | 본문을 고치고 "결정 변경 이력"에 날짜와 사유를 남긴다 | 코드보다 문서를 먼저 고친다 |

- 한 기능 안의 이름·구조 결정(예: 어느 클래스를 어느 패키지에 둘지)은 ADR이 아니라 설계 문서의 결정 사항 표에 적는다.
- 같은 사실은 한 곳에만 쓰고 다른 쪽에서는 링크한다. 설계 문서가 ADR의 결정을 따를 때는 결정을 다시 쓰지 않고 ADR을 가리킨다.

## 설계 완료 기준

- 모든 슬라이스에 테스트 케이스와 위험도가 적혀 있다.
- 열린 질문이 비어 있다. 남기려면 이유를 적는다.

## 위험도 기준

처음 시작하는 기준이며 사용하면서 조정한다.

| 위험도 | 영역 | 리뷰 깊이 |
|---|---|---|
| 높음 | 인증·권한(JWT, Spring Security), DB 마이그레이션(Flyway), 동시성, Outbox·Kafka consumer·Redis 캐시 정합성, 외부 연동(S3, 메일) | 한 줄씩 정독 |
| 중간 | 새 비즈니스 규칙(서비스, 엔티티 불변식), QueryDSL 동적 쿼리 | 테스트가 요구사항을 맞게 표현하는지 + 핵심 로직 정독 |
| 낮음 | CRUD, DTO, Converter 등 보일러플레이트 | 테스트 결과와 리뷰 요약 위주 |
